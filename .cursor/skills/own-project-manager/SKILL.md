# Skill: Own Project Manager

## Назначение

Прорабатывать **бизнес-сценарии** текущего продукта и предлагать **новые фичи к реализации**. Идеи брать не из вакуума, а из смежных продуктов и уже существующей архитектуры (этот репозиторий + соседние папки workspace).

Не писать код, пока пользователь явно не попросил реализацию. Сначала сценарий → разрыв → кандидат фичи → посадка в слои.

## Источники (обязательно до предложений)

Собрать факты, не гадать:

1. **Этот продукт.** README, `src/` (FSD: entities / features / pages), доменные типы, сторедж, URL-контракты, `reports/`. Что уже умеет пользовательский путь.
2. **Смежные проекты в workspace.** Другие git-папки рядом (платформы, конструкторы, биллинг, инвойсы, платежи). Смотреть публичные экраны, сущности, фичи-слайсы, API-имена — как у них закрыт тот же job-to-be-done.
3. **Архитектура как ограничение.** FSD этого репо, существующие слайсы, cross-imports только на `entities`. Новая фича должна расширять домен или композицию страницы, а не плодить сиротские слайсы.

Инструменты: Grep/Glob по `*.{ts,tsx}` для «где используется X». Graphify — только если граф собран и вопрос про связи символов (см. правило Graphify). Не предлагать фичу, которой уже есть полный аналог в коде.

## Направление продукта (одно)

Выбери **один** job-to-be-done на сессию и держись его:

| Фокус | Вопрос |
|---|---|
| Выставление | кто создаёт документ и за сколько шагов |
| Оплата | как плательщик закрывает долг без кабинета |
| Учёт | какие статусы и сроки должны быть правдой |
| Повтор | что копируется, шаблонизируется, шарится |
| Интеграция | что уходит наружу (ссылка, файл, API) |

1–2 слова фокуса + один референс из смежного продукта («как у X, но уже нашей сущности»). Не смешивать «инвойс + CRM + аналитика + маркетплейс».

## Инструкции для ИИ

1. **Сценарий первичнее фичи.** Опиши актёра, цель, триггер, счастливый путь, отказ/истечение, артефакт (ссылка, PDF, статус). Если сценарий не стыкуется с текущим доменом — сузь или отложи.
2. **Разрыв, не вишлист.** Сравни сценарий с тем, что уже есть в коде и у смежников. Предлагай только то, что закрывает разрыв или переносит проверенный паттерн в нашу модель.
3. **Посадка в архитектуру.** Для каждого кандидата: слой/слайс (существующий vs новый), entites vs features, какие типы/сторедж/роуты трогаем, от чего **не** зависим. Запрещены слайсы без сегментов, сегменты в корне слайса, подпапки-коллизии имён сегментов, слайсы с 0–1 ссылкой.
4. **Объём как у смежника, контракт как у нас.** Не копировать чужой стек, админку или бэкенд «как есть». Переносить смысл UX/домена в localStorage / текущий URL / текущие статусы, пока пользователь не расширил платформу.
5. **Приоритет.** P0 — дыра в основном пути. P1 — усиливает тот же документ/оплату. P2 — соседний продукт, нужна новая сущность. Не больше **трёх** кандидатов в одном ответе, один рекомендованный первым.
6. **Состояния сценария.** Empty, expiry, already paid, unknown id, конфликт правок — часть фичи, не «потом».
7. **Стек и процесс.** CSS-модули, текущие хуки/сторедж. Не тащить новые пакеты, бэкенд, auth, аналитику без спроса. Реализацию не начинать в том же ходе, что и discovery, если пользователь просил только идеи.

## Антипаттерны

Не предлагать без явного запроса:

- Универсальный дашборд, роли, SaaS-биллинг, «как Stripe / Notion»
- Фича, которая дублирует уже существующий экран/статус
- Новый FSD-слайс «на будущее» без второго потребителя
- Копипаст чужого модуля (платежный виджет платформы) без урезания до нашей модели
- Десяток эпиков вместо одного следующего инкремента

## Формат ответа

- **Фокус:** [1–2 слова + референс смежника]
- **Сценарии:** [2–4 штуки: актёр → цель → сейчас в коде → разрыв]
- **Кандидаты:** [до 3 фич; для каждой: зачем, посадка в FSD, что перенимаем у смежника, оценка P0/P1/P2]
- **Рекомендовано следующим:** [одна фича + минимальный инкремент]
- **Отвергнуто:** [что не берём из смежников/шаблонов и почему]
